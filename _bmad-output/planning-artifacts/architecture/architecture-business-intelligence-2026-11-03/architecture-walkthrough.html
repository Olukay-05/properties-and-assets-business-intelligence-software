Slide 01 — Executive Overview

Architecture Walkthrough & Developer Spine

A modular monolith for Nigerian facilities management (FM) companies, delivering undeniable operational proof of work without cloud or vendor lock-in.

🎯 The Product Goal

Give FM operators a reliable system where sites, assets, checklists, work orders, and proof photos are registered once and rendered into defensible client reports on demand.

📐 The 5 Standing Rules
  • No UI logic: Controllers & React components are thin adapters.
  • Unified service layer: Web, API, and future MCP invoke identical services.
  • No provider lock-in: Portable Postgres, S3 API, swappable tiles.
  • Strict tenancy: Session-only tenant resolution; RLS backstop.
  • Verified docs: Document what is tested, not what is planned.
⚡ Purpose of this Deck

Provide builders with the durable invariants that prevent architectural divergence across epics and stories. Every rule here binds the codebase.

💡 The Core Architecture Test
If two developers built their modules independently, could they make incompatible choices? If yes, this architecture fixes that call. Everything else is intentionally deferred.
Slide 02 — Scope Boundaries

The Three MVP Workflows

The MVP consists strictly of three complete workflows. Nothing ships until all three run end-to-end and pass automated tests.

➔
3. Client Reporting

✅ In Scope for Phase 1
  • Workflow 1: Organisation, client accounts, properties with canonical GPS points, zones, assets, and custody history.
  • Workflow 2: Versioned inspection templates, photo-verified visits, maintenance requests, and work order state machine.
  • Workflow 3: Client period reporting, dual PDF/CSV generation, and private signed URL evidence access.
  • Platform Foundations: Multi-tenancy (RLS + app scope), 6 core RBAC roles, audit log, and NDPA compliance readiness.
🚫 Explicitly Deferred (Do Not Build)
  • Client Self-Service Portal: Clients receive exported reports; no client login in v1.
  • External Integrations: No OAuth 2.1, no api_clients table, no webhooks, no MCP tools (Phase 3).
  • Native / Offline: Single responsive web application; no offline sync engine or desktop builds.
  • Complex Modules: No billing engine (pilots invoiced manually), no parts/inventory, no IoT sensors.

A clean, layered architecture inside a single Laravel codebase. External boundaries adapt incoming protocols into strongly-typed application service calls.

AD-1: Thin Adapters Rule

An adapter (Inertia or REST controller) only does 3 things:

  1. Validates HTTP request shape via FormRequest.
  2. Calls exactly one application service method.
  3. Maps the output to an Inertia response or { data, meta }.
AD-16: Typed Full-Stack Contracts

Every service accepts and returns Spatie Data objects. These DTOs automatically generate TypeScript definitions in resources/js/types/generated/, eliminating manual interface duplication.

Slide 04 — Security & Tenancy

Two-Layer Tenant Isolation

Isolation between FM companies is absolute. Application queries and database row-level security (RLS) form a defense-in-depth barrier.

Layer 1: Laravel TenantContext (App)
  • Session Only: Tenant is resolved exclusively from the authenticated user's memberships row.
  • Anti-Spoofing: organisation_id in request bodies or query params is rejected/ignored.
  • Global Scope: Eloquent auto-filters all queries by active organisation_id.
  • Model Hook: Model creating hook automatically stamps organisation_id.
Layer 2: PostgreSQL RLS (Database Backstop)
  • Enforced on all tenant tables:
    ENABLE ROW LEVEL SECURITY; FORCE RLS;
  • Policy:
    organisation_id = current_setting('app.org_id', true)::uuid
  • Connection Pooling Safety: Middleware issues SET LOCAL app.org_id = ? inside a transaction. Works seamlessly with Neon's transaction-mode PgBouncer pooler.
  • Non-Owner Role: Runtime connects as a role without BYPASSRLS.
⚠️ Non-Negotiable CI Gate (AD-19)
A tenant isolation matrix runs on every commit. For each core entity, it tests that Organisation B cannot access Organisation A's data across 5 layers: HTTP, Service, Raw SQL, Background Jobs, and Signed URLs.
Slide 05 — Geospatial Implementation

Canonical Geospatial Integrity

Coordinates are stored once in PostGIS. Metric distances are computed via the geography cast, eliminating classic coordinate inversion and degree errors.

Canonical Storage (AD-7)
  • PostGIS Column: properties.geom geometry(Point, 4326) with GiST indexing.
  • No Duplicate Columns: Latitude and longitude are never stored in separate columns; they are derived via ST_Y(geom) and ST_X(geom) in serializers.
  • Single Mutator: LocationService::setLocation() is the only code path that writes coordinates.
  • Append-Only History: Every coordinate change appends a locations history entry with accuracy, source, and timestamp.
Metric Distance & Maps
  • Metre Accuracy: All distance checks cast to ::geography inside a single helper:
    Geo::distanceMetres() and Geo::withinMetres().
  • No Raw ST_Distance: Running ST_Distance on raw geometry returns angular degrees (a critical bug); never permitted.
  • Frontend Map: Rendered via MapLibre GL JS + OpenFreeMap vector tiles wrapped in a single <PropertyMap> component.
  • Postcode Rule: Postcode is customer-entered reference text; never proves title or occupancy.
// Example canonical coordinate update
LocationService::setLocation($property, lat: 6.5244, lng: 3.3792, accuracyM: 5.0, source: 'mobile_gps');
// Executes: ST_SetSRID(ST_MakePoint(3.3792, 6.5244), 4326) and inserts into locations table.
Slide 06 — Domain Modularization

Module Boundaries & Table Ownership

Each table has exactly one owning module. Cross-module writes must go through the owner's application service.

Module Tables Owned (Exclusive Writers) Allowed Cross-Module Dependencies
Tenancy organisations, users, memberships, personal_access_tokens Base module; depended on by all.
Registry client_accounts, properties, locations, site_zones, assets, asset_custody Reads Tenancy. Assembles dynamic Asset Timeline (AD-9).
Inspections inspection_templates, inspection_template_items, inspections, inspection_responses Reads Registry, calls Evidence for photos. Calls Maintenance to raise faults.
Maintenance maintenance_requests, work_orders, work_order_events, contractors Reads Registry, calls Evidence for photos. Owns state machine (AD-11).
Evidence attachments Manages private R2 uploads and 10-minute signed URLs.
Reporting None (Read-only query service) Aggregates Registry, Inspections, Maintenance, and Evidence.
Audit audit_events Invoked atomically inside originating transactions.
🔒 Read-Only Eloquent Relations Rule (AD-2)
Eloquent relationships traversing domain boundaries (e.g. $workOrder->attachments()) are strictly read-only. Never call $workOrder->attachments()->create(); always call EvidenceService::attachPhoto()!
Slide 07 — Sub-Tenant Partitioning

Client Account Scoping

An FM company manages multiple client accounts. Permissions and data visibility must be strictly partitionable per client account.

The Denormalization Rule (AD-5)

Every client-owned entity carries a direct client_account_id column stamped immutably at creation from its parent property:

  • properties & site_zones
  • assets & asset_custody
  • inspections & inspection_responses
  • maintenance_requests & work_orders
  • attachments

Prevents: Slow, error-prone multi-table JOINs across modules to ascertain client ownership.

Enforcement Mechanism
  • User Scope: memberships.client_scope holds either null (full organization access) or an array of permitted client UUIDs.
  • Global ClientScope: A global Eloquent scope automatically injects whereIn('client_account_id', $scope) when a user has a restricted scope.
  • Service Authorisation: Services verify that target resources match the actor's permitted client accounts before mutation.
  • Technician Isolation: Technicians assigned to Client A can never view or complete work orders for Client B.
Slide 08 — Contracts & Error Handling

Full-Stack Data Contracts & Errors

Frontend and backend share deterministic data structures and standardized error responses.

TypeScript & DTO Synchronization (AD-16)
// app/Domain/Maintenance/Data/WorkOrderData.php
class WorkOrderData extends Data {
    public function __construct(
        public string $id,
        public string $title,
        public WorkOrderStatus $status,
        public ?string $assignedTechnicianId,
        public CarbonImmutable $createdAt
    ) {}
}

Runs through spatie/typescript-transformer to automatically generate exact TS types in resources/js/types/generated/ on build.

Unified Error Envelope (AD-17)

Services throw DomainException subclasses with permanent machine-readable codes:

// REST API error response (HTTP 422)
{
  "error": {
    "code": "work_order_invalid_transition",
    "message": "Cannot transition from Completed to In Progress."
  }
}

Inertia requests automatically translate domain exceptions into form validation errors or flash toasts.

Slide 09 — Runtime & Operations

Infrastructure & Operational Topology

Low-cost European hosting ensuring single-digit millisecond app-to-db latency, with verified backup and restore procedures.

🖥️ Compute & DB
  • App VPS: Hetzner (Germany), 4GB RAM (~$7–13/mo). Single Docker container runs Caddy, Laravel web, queue worker, and scheduler.
  • Database: Neon Postgres 17 + PostGIS 3.5 (Frankfurt). App-to-DB roundtrip is 3–5ms.
  • User Latency: Unavoidable user-to-EU latency from Lagos is ~110–150ms.
📦 Storage & Reports
  • Object Storage: Cloudflare R2 (zero egress fees). Private bucket for photos and report exports.
  • Signed URLs: Evidence served via 10-minute temporary signed URLs.
  • PDF Worker: Spatie Laravel PDF (Chromium). Queue worker concurrency constrained to 1 to prevent VPS RAM spikes.
🛡️ Backups & Portability
  • Dual Backups: Neon Point-in-Time Recovery (PITR) plus nightly pg_dump to a separate, isolated R2 bucket.
  • Restoration Drill: Documented and tested restore drill required before pilot launch.
  • Zero SDK Lock-in: S3-standard disk, standard Postgres. Repointing DB and storage moves the app to Nigeria if needed.
